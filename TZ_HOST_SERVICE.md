# ТЗ: приведение фундамента в порядок — вынос хоста из GUI-процесса

Документ-передача для новой сессии. Всё ниже — по факту, с указанием, что
проверено, а что гипотеза.

---

## 1. Зачем это делается

Видеоконвейер хоста живёт в одном процессе с egui-интерфейсом:
`HostService::start(config)` вызывается прямо из `EvertyDeskApp::new()`
(`src/main.rs`). Отсюда весь текущий класс проблем.

Живо наблюдаемые симптомы на связке dev-ПК ↔ Intel UHD 610:

| Состояние окна хоста | CPU/GPU | fps стрима | Удалённый ввод |
|---|---|---|---|
| Развёрнуто | **100%** | ~3 | работает |
| Свёрнуто | **0%** | ~2 | **не работает вообще** |

Сломаны **оба** состояния. Поэтому объяснение «GUI просто отъедает ресурсы»
покрывает только половину, и одним усмирением перерисовки не обойтись.

Дополнительно: окно хоста само попадает в захватываемый экран, поэтому любая
его перерисовка превращает каждый кадр в «движение» — кадры не схлопываются до
почти нулевых на статичном рабочем столе, а стабильно весят 77–160 КБ.

RustDesk, от которого проект происходит, запускает хост отдельным сервисом
ровно по этим причинам.

## 2. ФАЗА 0 — пропажа ввода при свёрнутом окне (делать первой)

Это баг корректности, а не производительности. Делается **до** рефакторинга:
нужна рабочая база, и баг может оказаться независимым от выноса.

### Уже исключено — перепроверять не нужно

* **`BLOCK_REMOTE_INPUT` не при чём.** Флаг ставится только явным действием
  пользователя: горячая клавиша Ctrl+Alt+B (`main.rs:3252`, `main.rs:3537`) и
  сброс в `false` (`main.rs:8220`, `main.rs:8289`). От состояния окна не
  зависит никак.
* **Двадцать вызовов `ctx.request_repaint()` в `main.rs:7015-7360` — не причина
  непрерывной перерисовки.** Они внутри `poll_hyperv_session` и опроса
  виртуалок, в ветках «пришло событие», то есть срабатывают по факту.

### Гипотеза №1 (главная): EcoQoS / Efficiency Mode Windows 11

Windows автоматически применяет энергетическое троттлинг-состояние к процессам
без видимых окон на переднем плане.

Это единственное известное объяснение, покрывающее **оба** симптома сразу:
и обвал fps до 2, и мёртвый ввод **при нулевой нагрузке**. Ключевая улика —
нагрузка падает не до «нормальной», а буквально до нуля: потоки не заняты
работой, их замедляет планировщик.

Проверять через `SetProcessInformation` с `ProcessPowerThrottling` и
`PROCESS_POWER_THROTTLING_STATE`, явно отказавшись от троттлинга. Так делают
OBS и RustDesk.

### Гипотеза №2: блокировка потока чтения relay

Ввод приходит и внедряется на этом же потоке
(`host.rs` → `handle_peer_message` → `inject_mouse`/`inject_key`). Если поток
где-то блокируется на отправке (в `video_pipeline.rs` есть блокирующий
`tcp_tx.send` для телеметрии), встанут одновременно и ввод, и видео.

### Гипотеза №3 (только для fps): DXGI Desktop Duplication

`capture.rs` сам отмечает, что на Windows 11 `AcquireNextFrame` ждёт композиции
DWM и на статичном экране даёт ~8 fps. Для игрового режима там предусмотрен кэш
последнего кадра (`is_game_mode_enc`), который должен позволять кодировать на
целевой частоте. Два кадра в секунду означают, что кэш не работает — проверить.

### Связанное: IDR-шторм (симптом развёрнутого окна, не отдельный баг)

Толстые кадры → потери у клиента → клиент просит ключевой кадр (`evrt_client.rs`,
при потере при сборке) → хост шлёт очередной большой IDR → снова потери.
Самоподдерживающийся цикл.

`IDR_MIN_FORCED = 300ms` (уже в коде) частоту ограничил — ключевые кадры
разошлись с соседних номеров до интервала 300–500 мс — но причину убрать не мог.
Повторяющийся узкий набор размеров 77к/88к/103к/135к согласуется с тем, что одно
и то же содержимое экрана кодируется как ключевой кадр снова и снова.

## 3. Ключевое архитектурное решение

**Один исполняемый файл, разные режимы запуска** (`--host-agent`,
`--approval-prompt`), а не отдельные бинарники.

Почему:

* В проекте уже есть headless-режимы (`run_cli_connect`, `--connect`,
  `--diagnose`) — точка входа готова.
* На macOS разрешения Screen Recording и Accessibility выдаются на **конкретный
  бинарь**. Второй файл потребовал бы повторной выдачи разрешений пользователем
  и отдельной подписи.
* Обновление одного файла проще и не рассинхронизируется по версиям.

## 4. Сложности, которые определяют порядок фаз

1. **Изоляция Session 0 (Windows) — главная ловушка.** Служба Windows работает
   в Session 0, у которой **нет доступа к рабочему столу**: она физически не
   может ни захватить экран, ни внедрить ввод. «Просто сделать службу» задачу
   не решает. Нужна двухуровневая схема: служба-супервизор в Session 0 плюс
   агент, запускаемый ею в интерактивной сессии пользователя через
   `WTSQueryUserToken` + `CreateProcessAsUser`.
2. **UAC и UIPI.** Чтобы вводить в окна с повышенными правами, агент сам должен
   быть повышен, иначе UIPI молча блокирует ввод.
3. **Защищённый рабочий стол.** Запрос UAC, Ctrl+Alt+Del и экран блокировки
   живут на отдельном desktop. Нужны `OpenInputDesktop`/`SetThreadDesktop` и
   перезапуск агента при переключении.
4. **Смена сессий.** Вход/выход пользователя, быстрое переключение, RDP. Служба
   обязана слушать `WTS_SESSION_LOGON`/`LOGOFF`/`LOCK` и пересоздавать агента.
5. **IPC.** Именованные каналы на Windows, unix-сокеты на Linux. Нужен
   протокол: статус, запрос подтверждения, конфиг, логи.
6. **Окно подтверждения входящего подключения.** Если хост работает без GUI,
   показать запрос некому. Нужен режим `--approval-prompt`: маленькое окно,
   которое агент поднимает сам, работает без основного GUI, всегда поверх окон
   и на нужном рабочем столе. Плюс защита от подмены: подтверждение должно
   приходить агенту по тому же IPC, а не через глобальное состояние процесса.
7. **Диагностика.** Сейчас всё пишет в один `evertydesk_host_log.txt`, и весь
   рабочий процесс отладки на этом построен. Логи трёх процессов надо свести
   обратно в один файл, иначе потеряем главный инструмент.
8. **Живучесть.** Умер агент — служба поднимает заново; умерла служба — поднимает
   SCM. Не должно быть состояния «сессия висит, а видео мертво».
9. **Совместимость.** Установка службы требует прав администратора. Одиночный
   запуск exe без установки обязан продолжать работать как сейчас.
10. **Linux/macOS.** systemd user service против системного; на macOS разрешения
    привязаны к бинарю (см. решение в разделе 3).

## 5. Фазы

Порядок выбран так, чтобы самое дорогое (Session 0, защищённый рабочий стол)
делалось последним, когда IPC и режимы запуска уже обкатаны на простом случае.
Каждая фаза самостоятельно ценна и проверяема.

### Фаза 0 — пропажа ввода
См. раздел 2. Начинать с проверки EcoQoS.

### Фаза 1 — хост отдельным процессом (ещё не служба)
Режим `--host-agent`. GUI поднимает его дочерним процессом, общение по
именованному каналу. Уже это снимает конкуренцию за ресурсы и позволяет свернуть
или закрыть GUI, не убивая стрим. **Низкий риск, основная часть выигрыша.**

### Фаза 2 — окно подтверждения
Режим `--approval-prompt`, поднимается агентом. Работает без основного GUI.

### Фаза 3 — служба Windows
Супервизор в Session 0 + запуск агента в сессии пользователя. Здесь живут
сложности 1–4. Самая дорогая фаза.

### Фаза 4 — Linux/macOS
Аналоги через systemd и launchd.

## 6. Что уже работает — не сломать при рефакторинге

Подтверждено живьём в предыдущей сессии:

* **oneVPL кодирует аппаратно мимо Media Foundation** без единой установки у
  пользователя. `src/onevpl.rs`, `src/onevpl_shim.cpp`, заголовки в
  `vendor/onevpl` (MIT). В логе: `Encoder каскад: oneVPL/H264 → …`.
* **Игровой режим включается по-настоящему** — `connect_game()` выставляет
  `ConnectMode::Game`, клиент просит конкретный аппаратный кодек.
* **Качество выправлено**: 3.0 → 7.8 Мбит/с. Игровой режим просил `Best`, а
  получал `Low` из-за правила `fps >= 45 → Low` в `initial_stream_quality`.
* **Смешивание кодеков внутри сессии устранено.** `Ok(None)` из бэкенда больше
  не проваливается к бэкенду с другим кодеком — это роняло клиент.
* **Артефакты EVRTCK** разобраны до двух причин рассинхрона XOR-базы и
  исправлены.
* **На Windows «Авто» в игровом режиме = H264.** Обоснование: системный
  HEVC-декодер Microsoft роняет клиент по одному и тому же адресу даже на
  заведомо корректном потоке (дамп разобран побайтно: VPS+SPS+PPS+SEI+IDR, Main,
  level 4.1, 1280 — всё верно). H265 в списке оставлен явным выбором с
  предупреждением; на Android он работает и там быстрее.

## 7. Как проверять

Стенд: dev-ПК (RTX 4060) ↔ вторая машина с Intel UHD 610.

1. `cargo build --release`
2. Скопировать `target/release/evertydesk-lite.exe` **на обе машины** — старый
   хост с новым клиентом даёт ложную картину.
3. Хост-лог: `evertydesk_host_log.txt` рядом с exe, перезаписывается при каждом
   запуске.

На что смотреть в логе:

* `Кодеки: …` / `D3D12 encode: …` / `oneVPL/MSDK: …` — возможности машины.
* `Encoder каскад: …` — какой бэкенд выбран.
* `EVRT SessionConfig: …` — объявленный кодек и битрейт.
* `EVRT sent_fps=… target=…` — реальная частота отправки.
* `EVRT: sending IDR …` — частота и размер ключевых кадров.
* `[perf] UI render: … fps (idle=…)` — реальная частота перерисовки GUI против
  ожидаемой.

Падение клиента ловится подключением отладчика к процессу: рантайм-паники
Rust пишутся в `%APPDATA%\EvertyDesk Lite\evertydesk_panic.log`, но жёсткие
крахи в системных DLL туда не попадают.
