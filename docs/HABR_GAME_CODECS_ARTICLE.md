## Личная завязка

Давайте честно: я запускал PS3-эмулятор на Android, чтобы на приставке играть хотя бы в старые игры. Tekken 6 работал, но Tekken 7 для меня все равно отдельная история.

BosconovichKOSTYZ, нам еще предстоит решить, кто сильнее: мой King или твой Босконович. Это потом.

А сейчас важнее другое: если маленькая Android-приставка умеет декодировать видео аппаратно, почему бы не использовать ее как тонкий игровой клиент? Не как полноценную игровую машину, а как экран, ввод и быстрый декодер. Хост где-то рядом или в сети рендерит игру, кодирует поток, а приставка принимает картинку, декодирует и показывает на телевизоре.

Пару лет назад у меня была навязчивая идея: сделать так, чтобы почти любой Android с аппаратным кодеком мог играть онлайн в тяжелые тайтлы. Я даже предлагал похожую идею местным компьютерным клубам: ночью железо простаивает, а простой можно превращать в ресурс. Пользователь подключается, играет, клуб получает загрузку оборудования.

Тогда меня не очень поняли.

Теперь мы снова подошли к этой идее, но уже через EvertyDesk.

## Эксперимент: 360p и апскейл на клиенте

Первый вопрос в удаленной игре не про красоту. Первый вопрос про задержку.

Если гнать с хоста честные 1080p или 1440p, то можно быстро упереться во все сразу:

- кодер тратит больше времени;
- битрейт растет;
- сеть начинает жить своей жизнью;
- декодер на слабом клиенте может не успевать;
- input lag становится заметнее, чем хотелось бы.

Поэтому мы проверили грубую идею: получать картинку в низком разрешении, например 360p, а на клиенте апскейлить ее до нормального размера окна.

Это не магия и не «нейросеть сделала 4K». Это инженерный компромисс.

Хост делает меньше работы. Сеть получает меньше данных. Клиент быстро декодирует маленький кадр и растягивает его локально. Для текста это может быть спорно, но для динамичной игры иногда важнее получить новый кадр быстрее, чем получить идеальную четкость.

## Как вообще появляется картинка

Упрощенно remote gaming pipeline выглядит так:

```text
игра на host
  -> захват кадра
  -> подготовка кадра
  -> кодирование
  -> сеть
  -> декодирование
  -> апскейл / рендер
  -> экран клиента
```

А в обратную сторону:

```text
геймпад / клавиатура / мышь
  -> клиент
  -> сеть
  -> host
  -> ввод в игру
```

И вот здесь начинается главный кошмар: каждый шаг должен быть быстрым. Не «быстрым в среднем», а стабильно быстрым. Один лишний буфер, одна лишняя копия кадра CPU <-> GPU, один неправильный pixel format, один неудачный fallback, и ощущение управления ломается.

В обычном удаленном доступе иногда можно пережить лишние 100 мс. В игре это уже не «чуть медленнее». Это «почему персонаж делает удар после того, как меня уже наказали».

## Кодеки: прекрасный ужас

Кодеки - это один из тех слоев, которыми все пользуются каждый день и почти никто не хочет думать, как они устроены.

Открыли видео в браузере? Кодек.

Позвонили по видеосвязи? Кодек.

Посмотрели стрим? Кодек.

Запустили remote desktop? Снова кодек.

Внутри там не просто «сжать картинку». Там оценка движения, предсказание блоков, GOP, keyframe, B-frame, rate control, bitrate, latency mode, color space, профили, уровни, аппаратные очереди и еще много вещей, от которых хочется поставить чайник и уйти гулять.

А теперь представьте, что все это не просто написано в коде, а частично реализовано на кремнии.

Описать кодер на уровне железа - это отдельный поклон инженерам. Когда GPU или SoC умеет H.264, H.265 или AV1 аппаратно, это не «там есть библиотека». Это реальные блоки внутри чипа, которые годами проектировали, проверяли и доводили до состояния «работает у миллионов людей».

Поэтому я не люблю фразу «да просто прикрути кодек». Там нет «просто».

## Зоопарк, в котором мы живем

На Windows есть Media Foundation.

Рядом живут DXVA и DXVA2.

Есть старые Microsoft MPEG-2 компоненты.

На macOS есть VideoToolbox.

На Linux есть VA-API, VDPAU, Vulkan Video, иногда GStreamer, иногда системный FFmpeg, иногда ничего нормально не собрано.

У NVIDIA есть NVENC/NVDEC.

У Intel есть Quick Sync.

У AMD есть свои аппаратные блоки через AMF и драйверные API.

У браузерного мира есть WebRTC, и там Google, Apple, Microsoft и весь остальной рынок годами договаривались, как передавать видео так, чтобы оно не разваливалось на каждом втором устройстве.

И да, AV1. Мой любимый. Он крутой. Не всегда самый простой для low latency, не всегда доступный аппаратно на старом железе, но технологически это очень сильная штука.

Проблема в том, что remote desktop не может жить в мире «у пользователя точно есть лучший декодер». У пользователя может быть старый ноутбук, странный драйвер, корпоративная сборка Windows, Linux без нужного пакета, Android-приставка с кривым MediaCodec или видеокарта, где аппаратный блок есть, но конкретный профиль не поддерживается.

Значит, нужен не один кодек. Нужен выбор пути.

## Почему не тащить ffmpeg.exe

FFmpeg - великий проект. Без иронии. Но класть рядом с клиентом `ffmpeg.exe` как внешний процесс для live remote desktop - плохой путь для нашего сценария.

Причины простые:

- большой размер поставки;
- отдельный процесс и IPC;
- сложнее контролировать latency;
- сложнее диагностировать ошибки на машине пользователя;
- вопросы лицензирования и сборочных конфигураций;
- хуже интеграция с D3D11, Media Foundation, NVENC и будущим zero-copy pipeline.

Для офлайн-конвертации видео внешний FFmpeg часто нормален. Для удаленного интерактивного потока, где каждый миллисекундный буфер важен, хочется прямой backend.

То есть не «запустить команду», а открыть аппаратный кодер через системный API и кормить его кадрами напрямую.

## Что уже есть в EvertyDesk Lite

В текущем EvertyDesk Lite кодеки развиваются в сторону прямого backend без внешнего `ffmpeg.exe`.

Сейчас логика такая:

- OpenH264 как понятный software fallback для H.264;
- Windows Media Foundation decode для VP9, H.265 и экспериментального AV1;
- Windows Media Foundation encode для H.264/H.265, если система дает аппаратный MFT;
- AV1 декодирование включается осторожно, отдельным флагом, потому что драйверы и MFT могут падать;
- дальше планируются прямые backend для NVENC, VideoToolbox, VA-API и других системных API.

Упрощенно это можно представить так:

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum VideoBackend {
    ScreenshotOnly,
    OpenH264,
    MediaFoundationH264,
    MediaFoundationH265,
    NvencH264,
    NvencH265,
    Av1Experimental,
}
```

Идея не в том, чтобы всегда выбирать самый модный вариант. Идея в том, чтобы выбрать лучший рабочий вариант на конкретной паре устройств.

Если host умеет аппаратно кодировать H.265, а клиент умеет аппаратно декодировать H.265 - отлично.

Если оба умеют AV1 и latency проходит по тестам - можно пробовать AV1.

Если клиент старый - откатываемся на H.264.

Если совсем плохо - показываем screenshot path, потому что даже медленная картинка лучше, чем неработающий клиент.

## Переговоры между устройствами

Чтобы аппаратные кодеки работали «если оба устройства могут», нужен handshake. Не по принципу «я хочу AV1», а по принципу «вот что я реально умею сейчас».

Host должен сказать:

```text
encode:
  h264: hardware/software, max_resolution, max_fps
  h265: hardware/software, max_resolution, max_fps
  av1: hardware/software, experimental

capture:
  d3d11: yes/no
  zero_copy: yes/no
```

Client должен сказать:

```text
decode:
  h264: hardware/software
  h265: hardware/software
  vp9: hardware/software
  av1: hardware/software/disabled

render:
  gpu: yes/no
  software: yes/no
  upscale: nearest/bilinear/fsr-like/future-ai
```

После этого выбирается профиль:

```text
1. минимальная задержка;
2. стабильный decoder;
3. приемлемый bitrate;
4. fallback, если поток развалился.
```

То есть кодек - это не настройка в меню. Это результат переговоров.

## 360p - это не деградация, а режим

Очень легко сказать: «360p? Ну это несерьезно».

Для кино - да, несерьезно.

Для документа с мелким текстом - спорно.

Для теста remote gaming на слабом клиенте - уже интересно.

Потому что в игре важны:

- задержка между нажатием и реакцией;
- стабильность кадра;
- отсутствие резких просадок;
- предсказуемый bitrate;
- возможность быстро восстановиться после потери пакетов или reset декодера.

Если клиент сам умеет аккуратно растянуть картинку и пользователь сидит на расстоянии от телевизора, 360p может оказаться лучше, чем дерганый 1080p.

Позже можно делать адаптивно:

```text
360p low latency
540p balanced
720p quality
1080p local network
```

А еще можно менять профиль на лету: меню игры, статичный экран, кат-сцена, динамичная драка - это разные нагрузки.

## Апскейл: от простого к умному

Первый апскейл может быть обычным:

- nearest для пиксельного теста;
- bilinear как простой вариант;
- bicubic или Lanczos там, где хватает ресурсов;
- shader-based upscale на GPU;
- в будущем FSR-like или ML-upscale, если это не ломает latency.

Главное правило: апскейл не должен съедать выигрыш, который мы получили на кодировании и сети.

Если мы сэкономили 20 мс на маленьком кадре, а потом потратили 35 мс на «умный» апскейл, это не оптимизация. Это красивая ошибка.

## Самая грязная часть: копии кадра

Про кодеки часто говорят так, будто вход и выход - это просто `Vec<u8>`.

В реальности быстрый pipeline хочет жить на GPU.

Идеальный путь на Windows выглядит примерно так:

```text
D3D11 Desktop Duplication
  -> ID3D11Texture2D
  -> Media Foundation encoder
  -> encoded bitstream
  -> network
  -> Media Foundation decoder
  -> GPU texture
  -> render
```

Если в середине сделать лишний readback в CPU-память, можно потерять весь смысл аппаратного кодера.

Поэтому «написать свой backend» в этом контексте означает не написать с нуля H.265. Это было бы безумием. Это означает написать прямой слой интеграции с системными аппаратными API:

- Media Foundation на Windows;
- NVENC/NVDEC для NVIDIA;
- VideoToolbox на macOS;
- VA-API/Vulkan Video на Linux;
- MediaCodec на Android.

Мы не заменяем инженеров, которые сделали кодек на кремнии. Мы учимся нормально подключаться к их работе.

## Где тут EvertyDesk

EvertyDesk Lite начинался как remote desktop-клиент, который должен запускаться там, где «просто поставьте драйвер» не вариант.

Но та же философия работает и для игрового потока:

- не верить, что устройство идеальное;
- проверять возможности на старте;
- иметь fallback;
- не привязываться к одному media pipeline;
- не тащить огромные внешние бинарники без необходимости;
- держать диагностику видимой;
- измерять latency, а не только FPS.

Remote desktop для поддержки и remote gaming - разные режимы, но технически они родственники. Оба гоняют картинку, ввод и состояние через сеть. Просто gaming намного жестче наказывает за лишнюю задержку.

## Что получилось сейчас

На текущем этапе у нас есть направление:

- Windows-клиент уже видит Media Foundation декодеры;
- VP9/H.265/AV1 decode можно проверять через системные MFT;
- H.264/H.265 encode идет в сторону прямого Media Foundation backend;
- NVIDIA обнаруживается, NVENC backend вынесен как отдельное направление;
- внешний `ffmpeg.exe` не нужен как обязательная часть;
- 360p + client upscale проверяется как low-latency режим;
- Android-приставка рассматривается как тонкий игровой клиент, если ее аппаратный decoder справляется.

Это еще не финальный продуктовый режим «нажал кнопку и все работает везде». Это инженерный слой, где мы убираем магию и смотрим, что реально умеет железо.

## Что осталось сделать

Нужно довести прямые encoder backend до нормального состояния:

- стабильный Media Foundation encode H.264/H.265;
- NVENC без внешних процессов;
- VideoToolbox для macOS;
- VA-API или Vulkan Video для Linux;
- MediaCodec для Android;
- нормальный handshake возможностей host/client;
- адаптивное разрешение и bitrate;
- метрики end-to-end latency;
- восстановление после падения decoder/MFT;
- gamepad input без лишней задержки;
- звук;
- UX-профили: support, game, low bandwidth, local network.

Отдельно нужно честно мерить:

```text
capture ms
encode ms
network ms
decode ms
render ms
input roundtrip ms
```

Пока этого нет, любые разговоры про «быстро» остаются ощущениями.

## Зачем это все

Потому что кодеки - это не декоративная галочка в настройках.

Для remote desktop кодек решает, будет ли оператор видеть экран без боли.

Для remote gaming кодек решает, будет ли игра ощущаться игрой.

Для слабого клиента кодек решает, можно ли вообще использовать устройство, которое уже лежит дома под телевизором.

Мне нравится идея, что Android-приставка за небольшие деньги может стать клиентом для тяжелой игры, а реальный рендер будет происходить там, где есть мощное железо. Это не новая мечта в индустрии, но каждый раз, когда пытаешься сделать это своими руками, быстро понимаешь: романтика заканчивается на первом странном decoder reset.

И вот тут начинается настоящая инженерия.

Не «поставьте ffmpeg».

Не «у меня на ноутбуке работает».

А прямые backend, аппаратные кодеки, fallback, диагностика и честные цифры по задержке.

Мы начали с удаленного доступа.

Потом добавили терминал.

Потом AI-подсказки.

Теперь полезли в кодеки, апскейл и игровые сценарии.

Похоже, нам снова было мало.
