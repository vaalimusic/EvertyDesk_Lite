# EVRT2 — Security

**Author:** Arthur Valiev
**Version:** 2026-draft-1 (ROADMAP.md Phase 4.2)

---

## Scope

EVRT2_PACKET.md defines two security-relevant wire fields: `AuthTag`
(32-bit truncated) and the `ENCRYPTED` flag. This document specifies both
and records honestly which is implemented.

## AuthTag — implemented

```
AuthTag = first 4 bytes of HMAC-SHA256(session_key, header[auth_tag=0] ‖ payload)
```

The 4-byte AuthTag field is zeroed before hashing (it cannot include
itself), the tag is computed over the rest of the 32-byte header plus the
payload, and the first 4 bytes of the result are written back into the
field. Verification recomputes the same way and compares.

Implementation: `src/evrt2_crypto.rs` (`sign_packet`/`verify_packet`),
wired into `Evrt2Session` as a single choke point — every `send_*` method
signs, `recv_one` verifies and silently drops (like a malformed packet)
anything that fails, counting the drop in `auth_failures()` so a caller
can still notice.

### Key exchange (honest gap)

The session key (`evrt2_crypto::generate_session_key`, 32 bytes from
OS-sourced entropy) is generated by the host and sent to the client as
`evrt2key=<64 hex chars>` appended to the same comma-joined endpoints list
`Misc::Evrt2ExperimentEndpoints` already carries the UDP candidates in —
the identical channel and pattern EVRT1's own `evrt_session_token` already
uses.

**This means AuthTag's guarantee is bounded by that channel's own
security.** The TCP relay connection carrying it may itself be encrypted
(RustDesk-compatible secure handshake) or plaintext (an unattended/
no-password test session can choose "insecure" — see `Peer chose insecure
(empty PublicKey) — plaintext` in host logs). AuthTag as implemented today
defends against a **third party** forging or tampering with UDP packets
*after* the key has been established over that channel — it is not a
substitute for securing the channel itself. Hardening key exchange (e.g.
requiring a secure relay handshake before EVRT2 will start, or deriving
the key from the relay's own established symmetric key instead of
generating and transmitting a new one) is future work, not done here.

## ENCRYPTED flag — implemented (ROADMAP.md Phase 4.3)

`EVRT2_PACKET.md` names AES-GCM-256 for the `ENCRYPTED` flag (bit 3).
**Deviation, stated up front:** this reuses this codebase's own
already-audited, already-tested NaCl `secretbox` (XSalsa20-Poly1305)
primitive — see `src/crypto.rs`, already used for the RustDesk-compatible
TCP relay's own encryption — rather than adding a second AEAD cipher
family (a new `aes-gcm` dependency) purely to match one spec sentence.
Both are AEAD constructions with equivalent security properties for this
use case; reusing a primitive this codebase already trusts is the more
defensible engineering call than introducing a second one.

```
ciphertext = secretbox_encrypt(enc_key, nonce, plaintext_payload)
enc_key    = SHA256(session_key ‖ "evrt2-encrypt-v1")   // separate from
                                                          // the AuthTag key
nonce      = SHA256(header_bytes_excluding_auth_tag)[..24]
```

Implementation: `src/evrt2_crypto.rs` (`encrypt_payload`/`decrypt_payload`),
wired into the same `Evrt2Session::send_signed`/`recv_one` choke point as
AuthTag — **Encrypt-then-MAC**: the payload is encrypted first, the
`ENCRYPTED` flag bit is set, then AuthTag is computed over the resulting
ciphertext (not the plaintext), and on receive AuthTag is verified before
any attempt to decrypt.

**Key derivation, not a dedicated wire field for the nonce.** The 32-byte
header has no spare bytes for a nonce, so it is derived deterministically
by hashing the packet's own header fields (FrameId, PacketIndex,
PresentationTimeUs, FEC fields, etc.) — unique per packet within a session
for any realistic session length, which is what a nonce needs (never
reused under the same key), without a wire format change.

**HELLO/ACK are deliberately unauthenticated and unencrypted on both
sides** — the key is only applied to a session's `Evrt2Session` *after*
the handshake completes (host: right after sending ACK; client: right
after receiving ACK), not at session construction. An earlier version of
this code set the key immediately, which silently encrypted the client's
own HELLO — the host's pre-session HELLO-wait loop decodes it with a raw
socket before any `Evrt2Session`/key exists to check it against, so the
parsed `max_fps`/`max_res` fields would have been ciphertext garbage. Real
bug, found and fixed before this shipped.

## Non-goals (this document, current draft)

- Forward secrecy / key rotation mid-session — the session key is fixed
  for the session's lifetime.
- Defense against a party that can read the TCP relay channel during key
  exchange (see above).
- Anything for the RELAY_WRAP (TCP-tunneled EVRT2) path — out of scope
  until that transport exists (ROADMAP.md Phase 5.3).
