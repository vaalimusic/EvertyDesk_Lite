## Фаза 0 — Ядро протокола ✅ (завершена, июль 2026)

Что доказано живым тестом (телефон Android ↔ ПК-хост, реальный WiFi):

- [x] Wire-формат: 32-байтный заголовок, magic `EVR2`, все типы пакетов (`evrt2_packet.rs`)
- [x] XOR FEC с coverage-классами `i mod K` + **self-describing length prefix** — найден и закрыт реальный протокольный баг: длина восстановленного пакета невосстановима без префикса (`evrt2_fec.rs`, `evrt2_session.rs`)
- [x] Сборка кадров из пакетов с FEC-восстановлением, мультигрупповые кадры (`evrt2_session.rs::FrameReassembler`)
- [x] Handshake HELLO→ACK, FEEDBACK, GOODBYE, IDR_REQUEST — рабочие хелперы
- [x] Adaptive jitter buffer по формуле спеки (EMA α=0.1, клампы 4–50ms / 2ms+ для 47) — живой на клиенте (`evrt2_jitter.rs`)
- [x] Attention Map из реальных сигналов (motion + focus + surprise; w_A=w_G=w_E=0 честно) (`evrt2_attention.rs`)
- [x] Task-01: visible region из карты внимания, send-order, VISIBLE_REGION флаг (bit 8), jitter-bypass, age-ceiling breach detection (`evrt2_scheduler.rs`)
- [x] Task-02: Capability Registry + калиброванный marginal-utility scheduler, замена `RAYON_THRESHOLD` (`execution_capability.rs`)
- [x] Режимы AR2R47: конфиги + state machine переходов — **реализовано и покрыто тестами, но не управляет живой сессией** (`evrt2_modes.rs`)
- [x] EVRT2-only вход: чекбокс на клиенте → `evrt2_only` в LoginRequest → хост пропускает EVRT1-пайплайн целиком (`host.rs::run_evrt2_only_session`)
- [x] Keepalive-дисциплина: FEEDBACK каждые 3с (UDP) + пустые фреймы 1/с (TCP relay) — оба правила рождены из реальных обрывов
- [x] Периодический keyframe (2с) — лечение «рассыпающейся» картинки при потерях

Известные честные ограничения текущего среза:
- 20 FPS фиксированно, CPU-кодек EVRTCK, без perf-тюнинга → заметная задержка
- Байтовые границы VISIBLE_REGION — оценка по среднему размеру тайла, не точные
- DEGRADE_SIGNAL логируется на хосте, на провод не уходит
- Нет шифрования (AuthTag=0), нет WAN (только LAN-кандидаты), один клиент

**Обнаружено, не устранено (наблюдение, июль 2026):** EVRT2-only сессия
изредка обрывается через ~30с–2мин с `TCP read header failed: failed to
fill whole buffer`, при этом keepalive с обеих сторон подтверждённо
работает (не флаппинг, не наш таймаут — интервалы до обрыва варьируются:
48с, 34с, 89с, что не похоже на фиксированный протокольный таймер). Похоже
на внешний фактор (relay периодически переиспользует соединения, либо
WiFi-радио телефона на секунду роняет связь в энергосбережении) —
корневая причина не найдена, авто-переподключение сознательно не
добавлено (не признано критичным для текущих тестов).

| 6.11 | Кросс-вендорный откат аппаратного энкодера — Intel Quick Sync / AMD через Media Foundation, если NVENC недоступен | ✅ живо проверено на NVIDIA (регрессии нет); ⚠️ не проверено на реальном Intel/AMD железе | Пользователь спросил, заработает ли EVRT2/H265 на двух его ПК с Intel-графикой — `nvenc_shim.cpp` целиком специфичен для NVIDIA SDK, без NVENC сессия молча откатывалась на CPU-only EVRTCK (~50-150мс/кадр под движением — тот самый медленный старт расследования этой сессии). Решение: НЕ писать отдельные нативные интеграции под Intel Media SDK/oneVPL и AMD AMF (это дни работы на каждого вендора, повторяющие объём `nvenc_shim.cpp`), а переиспользовать УЖЕ ГОТОВЫЙ `mf_encode.rs` — Windows Media Foundation сама перечисляет АППАРАТНЫЕ MFT-энкодеры (`MFT_ENUM_FLAG_HARDWARE`) вне зависимости от вендора; это официальный способ доступа к Intel Quick Sync/AMD-блоку от самих вендоров, не «медленная общая прослойка» — тот же самый путь, что уже работает в проде для EVRT1 (`host.rs` явно упоминает Intel Quick Sync). Добавлено в `evrt2_experiment.rs`: при неудаче открытия NVENC на калибровочном тике теперь пробуется `MfVideoEncoder::new(...)` (только если `mf_encoder_status()` подтверждает АППАРАТНЫЙ H265/H264 MFT — софтверный MFT намеренно игнорируется, он не лучше CPU_EVRTCK). `nvenc_forced_for_h265` обобщён до «NVENC ИЛИ MF активны» — MF, как и NVENC-forced случай, используется безусловно, без гонки с EVRTCK (нет смысла гонять синхронный CPU-вызов). `MfVideoEncoder::encode_bgra()` вызывается синхронно (без выделенного потока, в отличие от NVENC — не нужен, гонки всё равно нет) прямо в месте, где обычно принимается асинхронный ответ NVENC-воркера, и производит тот же тип `NvencPacket` — весь код ниже по потоку (`session.send_frame`, проверка сплайсинга, кэш codec_config) остался НЕТРОНУТЫМ, кодек-агностичным. Клиентская часть (Android) НЕ ИЗМЕНИЛАСЬ ВООБЩЕ — битовый поток H265/H264 на проводе идентичен независимо от того, кто его закодировал, декодер уже кодек-агностичен. Живо проверено: на RTX 4060 регрессии нет (NVENC по-прежнему открывается первым, decoded_fps/потери/AIMD не изменились, строка про MF-энкодер закономерно не появилась). НЕ проверено на реальном Intel/AMD — у пользователя есть такие машины, но недоступны из этой сессии; см. трекер задач (#38) за инструкцией, что смотреть в логе при следующей проверке |
| 6.12 | «Клиент закрывается после первого кадра» — обычное (не-EVRT2) подключение падало с access violation внутри `HEVCDECODER_STORE.dll` (системный HEVC-декодер Media Foundation от Microsoft) | ✅ живо подтверждено исправленным на связке dev-ПК↔Intel-ПК | Пользователь пожаловался, что при обычном подключении (без вкладки «Игра»/EVRT2-only) клиентское окно просто закрывается почти сразу. Хост-лог ничего не показывал (крах жёсткий, не rust `panic!` — его собственный паник-хук в `main.rs` не сработал, буфер лога не сбросился). Подключили отладчик Visual Studio к процессу клиента — он поймал реальное исключение: `0xC0000005` (нарушение прав доступа при чтении по нулевому адресу) внутри `HEVCDECODER_STORE.dll`, точно тот краш, что уже был задокументирован комментарием в `transport.rs:2758-2764` для TCP/классического пути согласования кодека (`preferred_codec`) — но, как выяснилось, НЕ для отдельного UDP-пути (`evrt_session.rs`), у которого была своя независимая логика выбора кодека. `evrt_session.rs:178-186` определял начальный `SessionConfig.codec`, отправляемый клиенту в первую очередь (до того как реальный кодек кадров подтверждается pipeline'ом), через `match config.display.codec { H264 => "H264", Av1 => "AV1", _ => "H265" }` — то есть **любое** не-H264/AV1 значение (включая дефолтный `CodecPreference::Evrtck`, тот самый, что стоит у большинства пользователей "из коробки") трактовалось как явный запрос H265. Клиент, получив `SessionConfig(H265)`, открывал Windows' HEVC MF-декодер — и тот падал, хотя реальные видео-кадры в этой же сессии шли уже H264 (`Pipeline: game codec commit → H264`, подтверждено логом хоста). **Фикс**: инвертировал catch-all — H265 теперь объявляется в начальном `SessionConfig` только при ЯВНОМ выборе пользователя (`CodecPreference::H265`), как и на TCP-пути; всё остальное (включая `Evrtck`/`Auto`) по умолчанию честно объявляет H264. Живо подтверждено на пересобранном билде: та же связка dev-ПК↔Intel-ПК подключилась на H264, кадры шли стабильно (`Frame received: evrt-N (H264)` без единого пропуска, host-энкодер прогрелся OpenH264-SW→MediaFoundation-hw за ~2с, actual_fps дошёл до целевых 15), сессия штатно завершилась `Отключено` по воле пользователя — без единого краша |
| 6.13 | «Обычное» подключение по умолчанию — EVRTCK (максимальная совместимость); настоящий per-connection выбор EVRT1/EVRT2 + кодека в UI PC-клиента | ✅ собирается чисто, `cargo build --release` зелёный; ⚠️ живой тест между двумя ПК не проведён в этой сессии (нужны два одновременных GUI-окна) | Пользователь попросил: (1) «обычное» подключение — через EVRTCK, чтобы работало на любом устройстве; (2) нормальный игровой режим между ПК с выбором EVRT1/EVRT2 и кодека, а не текущую единственную debug-галочку. Разведка архитектуры (см. агент этой сессии) нашла, что (1) `preferred_codec()` (`transport.rs:2765`) уже отправлял `PreferCodec::H264` для дефолтного `CodecPreference::Evrtck` вместо `Auto` — побочный эффект фикса #6.12, из-за которого хост НИКОГДА не включал EVRTCK для обычных подключений (`want_evrtck`, `video_pipeline.rs:145-151`, истинно только для `Auto`/`Vp9`). Исправлено: `Evrtck → Auto` без условия на `h264_capable` — теперь безопасно, поскольку сам крash-класс #6.12 уже закрыт на уровне `evrt_session.rs`, а `want_evrtck` — ОДИН и тот же `Arc<AtomicBool>`, общий между классическим TCP-пайплайном и UDP EVRT-сессией (подтверждено чтением `video_pipeline.rs:1897-1913`), так что фикс работает на обоих путях сразу. (2) Существующая кнопка «EVRT2-only тест» оказалась НЕ протокол-тестом без видео, как гласила подпись, а полноценным захватом+кодированием на хосте — но полностью ОТДЕЛЬНОЙ автономной сессией (`run_evrt2_only_session`, `host.rs:1122`), которая целиком заменяет обычную сессию (без мыши/клавиатуры, `control_only=true`, видео только в мелком плавающем превью). Для «нормального» игрового режима это не годилось — реализовывать ввод с нуля внутри изолированного протокол-рига было бы избыточно. Вместо этого нашёлся уже готовый, отдельный и НЕЗАТРагивающий обычную сессию механизм: `SessionCommand::StartEvrt2Experiment` → `Misc::Evrt2ExperimentRequest` (`host.rs:2917-2939`) запускает `evrt2_experiment::start_host_experiment` ПАРАЛЛЕЛЬНО обычному видео-пайплайну (тот не трогается, мышь/клавиатура продолжают работать как обычно), и клиент уже умеет декодировать эти кадры в `egui`-текстуру (`transport.rs:3413-3424`→`main.rs SessionEvent::Evrt2ExperimentFrame`) — просто раньше это шло только в маленькое плавающее окно превью. Добавлено: новый enum `GamePipeline{Evrt1,Evrt2}` и per-connection `connect_codec: CodecPreference` (НЕ пишутся в глобальный `AppConfig` — задаются на клон `DisplayConfig` только для этого подключения, чтобы не менять дефолт для будущих сессий); в панели подключения — переключатель EVRT1/EVRT2 и, для EVRT1, дропдаун кодека (переиспользован мёртвый код `codec_preference_order()`/`codec_status_text()` из `ui/settings.rs`, сделан `pub(crate)`). При выборе EVRT2 после успешного коннекта клиент шлёт `StartEvrt2Experiment` (тот же путь, что раньше срабатывал только для debug-галочки, но здесь — БЕЗ `control_only`/`evrt2_only`, обычная полнофункциональная сессия). `remote_screen_ui` теперь выбирает, какую текстуру рисовать: пока EVRT2-кадров не было — классический `remote_texture` (не даёт экрану быть пустым во время гонки UDP-кандидатов), как только пришёл первый EVRT2-кадр — переключается на него как на основной вид; плавающее превью-окно скрывается в этом режиме (стало избыточным, раз это уже основной вид). Честно: масштабирование экрана по-прежнему считается через `self.remote_size` (из классического пайплайна) — если EVRT2 закодировал в другом разрешении (даунскейл), возможен небольшой стретч картинки; маппинг мыши это не задевает, поскольку ввод всё так же идёт через неизменённый канал EVRT1. Кодек EVRT2 пока не выбирается вручную (хост сам решает NVENC/MF/EVRTCK по каскаду) — H265-декод для EVRT2 на Windows-клиенте не реализован (только Android Surface-путь), поэтому пикер кодека для EVRT2 сознательно не добавлен в этот раз, чтобы не предлагать нерабочую опцию. **Не проверено живым тестом** между двумя ПК в этой сессии — только компиляция/сборка; следующий шаг — реальное подключение с выбором EVRT2 и проверка, что видео действительно переключается на основной вид, а ввод остаётся живым |

## Порядок и зависимости

```
Фаза 1 (перф + Task-01)  ──┐
                            ├──► Фаза 2 (режимы) ──► Фаза 3 (APF)
Фаза 4 (безопасность) ─────┤         │
Фаза 5 (WAN) ──────────────┘         ▼
                              Фаза 6 (silicon + продукт)
```

Фазы 1, 4, 5 независимы друг от друга и могут идти параллельно.
Фаза 2 опирается на 1 (нельзя оценивать переходы режимов на 20 FPS).
Фаза 6 — финальная сборка, требует всего остального.
